## 18. Verificação de vulnerabilidades

Esta etapa executa uma sessão de verificação com uma ferramenta automatizada de teste de segurança. O objetivo não é acumular alertas, e sim interpretá-los e confrontá-los com os riscos que levantamos nas etapas anteriores.

### 18.1 Ambiente testado e autorização

O Comer-Tchê! foi modelado, mas não implementado. Não existe aplicação nossa para apontar a ferramenta. Usamos então a alternativa prevista no enunciado: uma aplicação deliberadamente vulnerável, executada para fins educacionais.

| Item                | Valor                                                                  |
| ------------------- | ---------------------------------------------------------------------- |
| Alvo                | OWASP Juice Shop **v20.2.0**                                           |
| Origem              | Imagem oficial `bkimminich/juice-shop` ([Docker Hub](https://hub.docker.com/r/bkimminich/juice-shop)) |
| Execução            | Container Docker local, exposto apenas em `localhost:3000`              |
| Rede                | Rede Docker isolada (`es-seguro`), sem exposição para a internet        |
| Base de autorização | Aplicação criada e mantida pela OWASP para treino em segurança          |

**Nenhum sistema de terceiros foi testado.** O alvo roda na máquina de quem executou a verificação, responde somente em `localhost` e existe justamente para ser analisado.

O Juice Shop é uma loja online. Tem catálogo, carrinho, contas de usuário e área administrativa. É essa semelhança com o Comer-Tchê! que permite trazer os resultados de volta para o nosso modelo de ameaças.

### 18.2 Ferramenta e configuração do teste

| Item        | Valor                                                              |
| ----------- | ------------------------------------------------------------------ |
| Ferramenta  | **OWASP ZAP 2.17.0** (imagem `zaproxy/zap-stable`)                 |
| Modo        | `zap-baseline.py` (varredura passiva)                              |
| Data/hora   | 11/08/2026, 20:47 UTC                                              |
| Escopo      | `http://juiceshop:3000`, a partir da rede interna do Docker         |
| Saídas      | `relatorio-zap.html` e `relatorio-zap.json`                         |

O modo baseline foi escolhido de propósito. Ele navega pela aplicação e analisa as respostas, mas não dispara ataques. Não injeta dados maliciosos nem tenta explorar falhas. Isso atende ao enunciado, que dispensa explorar as vulnerabilidades e pede a interpretação dos resultados.

Comando executado, com as imagens fixadas pelo digest para que a verificação possa ser repetida com as mesmas versões:

```bash
docker network create es-seguro

# OWASP Juice Shop v20.2.0
docker run -d --name juiceshop --network es-seguro -p 3000:3000 \
  bkimminich/juice-shop@sha256:73c53fbf442e8337b3ea3d98c7e8550308854701ebdfce4cc39768f36b75430e

# OWASP ZAP 2.17.0, varredura baseline (passiva)
docker run --rm --network es-seguro -v "$PWD/zap-out:/zap/wrk:rw" \
  zaproxy/zap-stable@sha256:781a2bdaea47324e7bab583e2263f21d257b0aee61ed51521a5be45f5f5081ef \
  zap-baseline.py -t http://juiceshop:3000 \
  -r relatorio-zap.html -J relatorio-zap.json -I
```

Usar a etiqueta `latest` não seria suficiente, porque ela muda com o tempo. Uma versão diferente do Juice Shop ou do ZAP produz outro conjunto de alertas. O digest identifica o conteúdo exato de cada imagem.

### 18.4 Análise dos achados

Analisamos os três alertas de maior severidade e maior relação com o nosso sistema.

| ID  | Alerta ou achado | Evidência | Possível impacto | Relação com OWASP ou CWE | Correção proposta |
| --- | ---------------- | --------- | ---------------- | ------------------------ | ----------------- |
| A01 | Content Security Policy (CSP) Header Not Set. Risco **Médio**, confiança alta | Resposta de `http://juiceshop:3000` sem o cabeçalho `Content-Security-Policy`, confirmado também com `curl -I` | O CSP é o cabeçalho que diz ao navegador de quais origens ele pode carregar script e estilo. Sem ele, um script injetado na página executa sem nenhuma restrição, o que permite roubo de sessão, leitura do que está na tela e ações em nome da vítima | **A05:2021** Security Misconfiguration, **CWE-693** Protection Mechanism Failure | Enviar um `Content-Security-Policy` restritivo, começando por `default-src 'self'` e sem `unsafe-inline`. Publicar antes em modo `Report-Only`, que registra o que seria bloqueado sem quebrar a aplicação |
| A02 | Cross-Domain Misconfiguration. Risco **Médio** | Cabeçalho `Access-Control-Allow-Origin: *` em `/`, `/robots.txt`, `/sitemap.xml` e `/styles.css` | Esse cabeçalho autoriza outros sites a ler a resposta. Com o coringa `*`, qualquer página consegue ler o que essa origem devolve ao navegador da vítima. Em uma API de pedidos isso amplia qualquer falha de autorização, porque o dado vazado passa a ser legível por um site do atacante | **A05:2021** Security Misconfiguration, **CWE-264** Permissions, Privileges and Access Controls | Trocar o `*` por uma lista fixa de origens confiáveis, com o aplicativo e o painel administrativo. Nunca combinar origem liberada com `Access-Control-Allow-Credentials: true` |
| A03 | Dangerous JS Functions. Risco **Baixo** | Chamada a `bypassSecurityTrustHtml(` em `http://juiceshop:3000/main.js` | O Angular remove marcação perigosa antes de exibir conteúdo. Essa função desliga essa proteção de propósito. Texto vindo do usuário volta a ser interpretado como HTML, o que abre Cross-Site Scripting, a injeção de script na página que a vítima carrega | **A03:2021** Injection (XSS), **CWE-749** Exposed Dangerous Method or Function | Remover a chamada e exibir o conteúdo por interpolação normal. Se a marcação for mesmo necessária, filtrá-la no servidor por lista de permissão antes de gravar |

Duas leituras que a ferramenta não entrega sozinha:

- **O A02 é menos grave do que o rótulo sugere, neste caso.** Com `Access-Control-Allow-Origin: *` o navegador não envia cookies nem cabeçalhos de autenticação na requisição cruzada, porque o próprio padrão CORS proíbe combinar o coringa com credenciais. Hoje o alerta atinge apenas conteúdo público. A correção continua valendo: no dia em que um endereço autenticado herdar essa configuração, a falha passa a expor dado real e sem aviso.
- **O A01 não é uma vulnerabilidade isolada**, e sim a ausência de uma camada de defesa. Ele só causa dano quando somado a outra falha. É o argumento de defesa em profundidade aplicado a um caso concreto: nenhuma barreira única deve ser a última.

#### Relação com os riscos e vulnerabilidades das etapas anteriores

| Achado | Risco do nosso registro (seção 8.4) | Vulnerabilidade catalogada (seção 11.2) | Como se relacionam |
| ------ | ----------------------------------- | --------------------------------------- | ------------------ |
| A01 | Nenhum | Nenhuma | Nenhuma das onze ameaças da Etapa 1 tratou de cabeçalhos de resposta. O achado se liga à Decisão 4 da Etapa 3, de defesa em profundidade na borda, mas reforça uma camada que não chegamos a modelar |
| A02 | **R07**, leitura de pedidos de outros clientes | IDOR, também chamada BOLA (**CWE-639**, API1:2023), em que o usuário troca o identificador do recurso na requisição | As duas se somam. O R07 permite ler o pedido alheio, e um CORS permissivo tornaria esse dado legível a partir de um site controlado pelo atacante, sem que a vítima perceba |
| A03 | Nenhum diretamente, mas a mesma raiz de R03, R04 e R07 | Parameter Tampering (**CWE-472**), por analogia | Não modelamos XSS. Ainda assim, o `bypassSecurityTrustHtml` repete o defeito que a seção 8.7 apontou como padrão dos nossos riscos de maior alcance: um ponto do sistema confia em dado vindo de fora sem validar. É o que a Prática 2 da Etapa 4 existe para impedir |

O cruzamento expõe uma lacuna no nosso próprio modelo de ameaças. Dois dos três achados não correspondem a risco algum do registro. O STRIDE que aplicamos olhou para identidade, dados e permissões, mas não para configuração de infraestrutura nem para injeção no navegador. Revisando a Etapa 1 hoje, caberiam ao menos mais duas ameaças: uma de Information Disclosure por cabeçalhos ausentes e uma de Tampering por conteúdo renderizado sem filtragem.

### 18.5 Alertas descartados

Dos onze tipos de alerta, oito ficaram fora da análise principal. Os motivos:

| Alerta | Classificação | Por que foi descartado |
| ------ | ------------- | ---------------------- |
| Timestamp Disclosure - Unix | **Falso positivo** | A regra sinaliza qualquer número de 10 dígitos como possível data exposta. As cinco ocorrências estão todas em `styles.css`, e duas delas mostram o engano. `1636363636` e `1818181818` são as dízimas de 16,36363636% e 18,18181818%, larguras de coluna comuns em folhas de estilo. Além disso, o próprio ZAP calcula que `1818181818` corresponde a 2027-08-13, uma data no futuro. Não há timestamp sendo exposto |
| Modern Web Application | Informativo | Registra apenas que a aplicação depende muito de JavaScript e que alguns links podem escapar do rastreamento automático. Não descreve falha |
| Storable and Cacheable Content, Storable but Non-Cacheable Content, Non-Storable Content | Informativos e sobrepostos | As três descrevem a mesma política de cache por ângulos diferentes. Só seriam relevantes se houvesse dado sensível em resposta armazenável, o que não ocorre nas URLs apontadas (`/robots.txt`, `/styles.css` e o favicon) |
| Cross-Origin-Opener-Policy, Cross-Origin-Embedder-Policy Header Missing | Agrupados com o A01 | Não são duplicatas do A01. O CSP restringe de onde a página carrega conteúdo, enquanto esses dois tratam de isolamento entre origens em outra camada do navegador. Foram agrupados porque a correção é a mesma frente de trabalho, definir os cabeçalhos de segurança na resposta do servidor, e porque isoladamente não representam exposição em uma aplicação que ainda não isola contextos |
| Deprecated Feature Policy Header Set | Baixo, sem impacto de segurança | A aplicação envia `Feature-Policy: payment 'self'`, cabeçalho substituído pelo `Permissions-Policy`. É dívida técnica de padronização, não exposição de dado |

### 18.6 Limitações desta verificação

O resultado mais importante desta etapa é o que a ferramenta não encontrou.

Nenhum dos seis riscos críticos do nosso registro apareceu no relatório, e não porque estejam tratados. Uma varredura passiva não consegue vê-los:

- **R07 (IDOR) e R10 (elevação de privilégio)** exigem duas contas autenticadas e o conhecimento de qual recurso pertence a quem. O ZAP não tem como saber que o pedido `1002` deveria ser invisível para o cliente do pedido `1001`. Isso é regra de negócio, e não padrão de resposta HTTP.
- **R01 (uso indevido de conta)** depende de testar credenciais, o que a ferramenta não faz em modo baseline.
- **R09 (indisponibilidade no pico)** só apareceria em um teste de carga, que é outro tipo de ensaio.

Somam-se a isso três limites da própria sessão:

1. **Sem autenticação.** O ZAP navegou como visitante anônimo, então toda a área logada ficou fora do alcance.
2. **Sem varredura ativa.** Como nenhum dado malicioso foi injetado, SQL Injection e XSS refletido não seriam detectados ainda que existissem, e o Juice Shop tem os dois.
3. **O alvo não é o nosso sistema.** Os resultados valem como aprendizado sobre classes de problema e sobre como ler a ferramenta, não como retrato do Comer-Tchê!.

A conclusão prática é que ferramenta automatizada e modelagem de ameaças são complementares, e não substitutas. O ZAP apontou em minutos três problemas de configuração que a nossa análise não previa, conforme a seção 18.4. Em compensação, ficou cego justamente para os riscos que classificamos como críticos, porque eles dependem de entender o negócio. Confiar somente na ferramenta produziria um sistema de cabeçalhos corretos e uma falha de autorização expondo a base inteira de clientes.
