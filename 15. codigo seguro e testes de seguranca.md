## 15. Código seguro e testes de segurança

### 15.1 Escolha das práticas

1. **Controle de autorização no servidor (RBAC + Ownership Check)** — decorre diretamente da Decisão de arquitetura 1 (seção 13) e dos requisitos RS01/RS02 (seção 11).
2. **Validação de entrada e integridade de dados (recálculo de preço no servidor + validação de assinatura de webhook)** — decorre da Decisão de arquitetura 2 (seção 13) e do requisito RS04 (seção 11).

Essas duas práticas foram escolhidas em vez de MFA (RS03) ou armazenamento de senhas porque já possuem risco, requisito e decisão de arquitetura totalmente formalizados nas etapas anteriores, o que garante coerência direta com o restante do trabalho e reduz o tempo de justificação.

### 15.2 Prática 1 — Controle de autorização (RBAC + Ownership Check)

**Risco e requisito relacionados**
- **R10** — Elevação de privilégio / obtenção de funções administrativas.
- **R07** — Leitura de pedidos de outros clientes (IDOR/BOLA).
- **Requisitos:** RS01 e RS02 (seção 11.1).
- **Decisão de arquitetura:** Decisão 1 — Validação centralizada de autorização via Middleware (seção 13).

#### 15.2.1 Testes de segurança (definidos antes da implementação)

| Teste | Entrada ou ação | Resultado esperado |
| --- | --- | --- |
| TS01 | Administrador autenticado (perfil `ADMIN`) faz `GET /api/v1/admin/users` | Requisição permitida, retorna a lista de usuários (`200 OK`) |
| TS02 | Cliente autenticado (perfil `CLIENTE`) faz `GET /api/v1/admin/users` diretamente pela API, sem passar pela interface | Requisição recusada (`403 Forbidden`) e evento registrado no log de auditoria |
| TS03 | Cliente autenticado faz `GET /api/v1/orders/{id}` de um pedido que é seu | Requisição permitida, retorna os dados do próprio pedido (`200 OK`) |
| TS04 | Cliente A autenticado faz `GET /api/v1/orders/{id}` de um pedido pertencente ao Cliente B | Requisição recusada (`403 Forbidden` ou `404 Not Found`) e evento registrado no log de auditoria |

#### 15.2.2 Implementação (pseudocódigo)

```
função authMiddleware(req):
    token = extrair_token(req.headers.authorization)
    se token inválido ou expirado:
        retornar 401 Unauthorized

    usuario = decodificar_token(token)     // contém id e perfil (papel)
    req.usuario = usuario
    continuar()

função rbacMiddleware(perfisPermitidos):
    retornar função(req):
        se req.usuario.perfil não está em perfisPermitidos:
            registrar_log_auditoria(req.usuario.id, "ACESSO_NEGADO_RBAC", req.rota)
            retornar 403 Forbidden
        continuar()

função ownershipMiddleware(req):
    pedido = buscar_pedido_no_banco(req.params.order_id)
    se pedido é nulo:
        retornar 404 Not Found
    se pedido.cliente_id != req.usuario.id E req.usuario.perfil != "ADMIN":
        registrar_log_auditoria(req.usuario.id, "TENTATIVA_IDOR", req.rota)
        retornar 403 Forbidden
    req.pedido = pedido
    continuar()

// Aplicação nas rotas — negação por padrão
rota.get("/api/v1/admin/users", authMiddleware, rbacMiddleware(["ADMIN"]), handlerListarUsuarios)
rota.get("/api/v1/orders/:order_id", authMiddleware, ownershipMiddleware, handlerBuscarPedido)
```

#### 15.2.3 Resultado esperado

Toda requisição a uma rota protegida passa obrigatoriamente pela verificação de perfil (RBAC) e, quando aplicável, pela verificação de propriedade do recurso (ownership), antes de qualquer lógica de negócio ser executada. Chamadas não autorizadas retornam `403 Forbidden` e geram um evento de auditoria, exatamente como definido no resultado esperado da Decisão 1 (seção 13).

### 15.3 Prática 2 — Validação de entrada e integridade de dados (recálculo de preço + validação de webhook)

**Risco e requisito relacionados**
- **R03** — Pedido com valor adulterado.
- **R04** — Pedido liberado sem pagamento confirmado.
- **Requisito:** RS04 (seção 11.1).
- **Decisão de arquitetura:** Decisão 2 — Autoridade total do servidor para cálculo de preços e pagamentos (seção 13).

#### 15.3.1 Testes de segurança (definidos antes da implementação)

| Teste | Entrada ou ação | Resultado esperado |
| --- | --- | --- |
| TS05 | Cliente monta pedido com itens que somam R$ 50,00 e envia o checkout | Servidor recalcula o total a partir da tabela de preços do banco (R$ 50,00) e processa a cobrança correta |
| TS06 | Atacante intercepta a requisição de checkout (ex.: via proxy) e altera o campo `total_amount` para R$ 0,01 | Servidor ignora o valor recebido do app, recalcula R$ 50,00 a partir do banco, processa a cobrança correta e registra alerta de divergência no log |
| TS07 | Gateway de pagamento envia webhook de confirmação com assinatura HMAC-SHA256 válida | Assinatura validada com sucesso; pedido é liberado para o restaurante |
| TS08 | Uma requisição forjada simula uma confirmação de pagamento com assinatura ausente ou incorreta | Requisição rejeitada (`401 Unauthorized`), pedido permanece não liberado, evento registrado no log de auditoria |

#### 15.3.2 Implementação (pseudocódigo)

```
função calcularTotalPedido(itensRecebidos):
    total = 0
    para cada item em itensRecebidos:
        itemBanco = buscar_item_no_banco(item.id)   // preço nunca vem do cliente
        total = total + (itemBanco.preco * item.quantidade)
    retornar total

função checkout(req):
    total_real = calcularTotalPedido(req.body.itens)
    // req.body.total_amount enviado pelo app é DESCARTADO
    pedido = criar_pedido(req.usuario.id, req.body.itens, total_real)
    enviar_para_gateway(pedido.id, total_real)
    retornar 200, pedido

função validarWebhookPagamento(req):
    assinaturaRecebida = req.headers["x-signature"]
    assinaturaCalculada = HMAC_SHA256(segredo_compartilhado, req.corpo_bruto)

    se assinaturaRecebida != assinaturaCalculada:
        registrar_log_auditoria(nulo, "WEBHOOK_ASSINATURA_INVALIDA", req.ip)
        retornar 401 Unauthorized

    pedido = buscar_pedido(req.body.pedido_id)
    se pedido.total != req.body.valor_confirmado:
        registrar_log_auditoria(pedido.id, "DIVERGENCIA_VALOR_WEBHOOK", req.body)
        retornar 400 Bad Request

    liberar_pedido(pedido.id)
    retornar 200 OK
```

#### 15.3.3 Resultado esperado

O valor cobrado do cliente nunca depende do que o aplicativo envia: o servidor é a única fonte da verdade para o preço, e qualquer notificação de pagamento sem assinatura válida é descartada. Isso elimina fraudes de adulteração de preço e impede a liberação de pedidos sem confirmação legítima de pagamento, conforme o resultado esperado da Decisão 2 (seção 13).
