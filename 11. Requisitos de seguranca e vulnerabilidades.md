## 11. Requisitos de segurança e vulnerabilidades

Nesta etapa, os riscos mais críticos identificados na Etapa 2 (NIST CSF 2.0) foram convertidos em requisitos formais de segurança para o **Comer-Tchê!**, associando cada um às vulnerabilidades catalogadas em padrões reconhecidos internacionalmente (**CWE**, **OWASP Top 10:2021** e **OWASP ASVS v4.0**).

### 11.1 Requisitos de segurança

Abaixo definimos os requisitos de segurança que o sistema precisa cumprir para resolver os riscos mais graves que identificamos. Para cada requisito, colocamos um critério claro de verificação para podermos testar na prática se a proteção está funcionando de verdade.

| ID | Risco de origem | Requisito de segurança | Critério de verificação |
| :--- | :--- | :--- | :--- |
| **RS01** | **R10** (Elevação de privilégio) | O servidor backend deve validar o perfil do usuário e suas permissões explícitas em 100% das requisições para rotas administrativas. | Qualquer requisição para `/api/v1/admin/*` realizada com token JWT contendo perfil `CLIENTE` ou `ENTREGADOR` deve retornar status HTTP `403 Forbidden` e registrar log de auditoria. |
| **RS02** | **R07** (Leitura de pedidos via IDOR) | A API deve verificar o vínculo de propriedade (*ownership check*) entre o usuário autenticado e o recurso solicitado antes de retornar dados sensíveis. | Uma requisição `GET /api/v1/orders/{order_id}` do Usuário A tentando acessar um `{order_id}` pertencente ao Usuário B deve retornar obrigatoriamente HTTP `403 Forbidden` ou `404 Not Found`. |
| **RS03** | **R01** (Uso indevido de conta / Credential Stuffing) | O sistema deve exigir verificação adicional (MFA/OTP) sempre que identificar um login vindo de um dispositivo ou endereço IP não reconhecido. | Requisições de login originadas de um `User-Agent` ou IP inédito devem gerar status temporário `MFA_PENDING`, bloqueando transações até a validação correta do código enviado por e-mail/SMS. |
| **RS04** | **R03 / R04** (Adulteração de preço e pagamento) | O servidor deve recalcular integralmente o valor do pedido a partir do banco de dados e validar a assinatura criptográfica dos webhooks do gateway. | Submeter um payload JSON no checkout contendo `"total_amount": 0.01` para um pedido de R$ 50,00 deve resultar no processamento da cobrança exata de R$ 50,00 no gateway e registro do alerta. |

### 11.2 Vulnerabilidades catalogadas

Aqui relacionamos cada risco a uma falha de segurança conhecida na literatura (como as listas da OWASP e o catálogo CWE). Isso ajuda a dar o nome técnico correto para o problema e mostrar exatamente como ele afeta o nosso aplicativo de delivery.

| Risco | Vulnerabilidade ou categoria | Referência utilizada | Relação com o Comer-Tchê! |
| :--- | :--- | :--- | :--- |
| **R10** | **Broken Function Level Access Control** (Controle de Acesso Quebrado em Nível de Função) | • **OWASP Top 10:** A01:2021 – Broken Access Control<br>• **CWE-285:** Improper Authorization<br>• **OWASP ASVS:** V4.1 Access Control | Ocorre quando a interface do aplicativo oculta o botão do painel administrativo, mas a API não verifica se o token pertence a um administrador quando chamada diretamente. |
| **R07** | **Insecure Direct Object Reference (IDOR)** / BOLA | • **OWASP API Top 10:** API1:2023 – Broken Object Level Authorization<br>• **CWE-639:** Authorization Bypass Through User-Controlled Key | Ocorre quando a API utiliza identificadores sequenciais e previsíveis em URLs (`/orders/1001`), permitindo que um atacante altere o número e leia dados e endereços de outros clientes. |
| **R01** | **Weak Authentication / Credential Stuffing** | • **OWASP Top 10:** A07:2021 – Identification and Authentication Failures<br>• **CWE-307:** Improper Restriction of Excessive Authentication Attempts | Permite que atacantes utilizem listas de senhas vazadas em outros sites para invadir contas no Comer-Tchê!, aproveitando a ausência de MFA ou de verificação de contexto de acesso. |
| **R03 / R04** | **Parameter Tampering / Software and Data Integrity Failures** | • **OWASP Top 10:** A08:2021 – Software and Data Integrity Failures<br>• **CWE-472:** External Control of Assumed-Immutable Web Parameter | Acontece quando o servidor confia no preço enviado pelo aplicativo móvel ou aceita notificações HTTP de pagamento sem validar a assinatura HMAC enviada pelo gateway parceiro. |
