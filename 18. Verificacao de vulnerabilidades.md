## 18. Verificação de vulnerabilidades

Esta etapa executa uma sessão real de verificação com uma ferramenta de teste de segurança
e interpreta os resultados, relacionando-os aos riscos e vulnerabilidades levantados nas
etapas anteriores.

### 18.1 Ambiente testado e autorização

O Comer-Tchê! é um sistema modelado, não implementado: não existe aplicação nossa para
apontar a ferramenta. Por isso usamos a alternativa prevista no enunciado — uma aplicação
deliberadamente vulnerável executada para fins educacionais.

| Item                | Valor                                                                  |
| ------------------- | ---------------------------------------------------------------------- |
| Alvo                | OWASP Juice Shop **v20.2.0**                                           |
| Origem              | Imagem oficial `bkimminich/juice-shop` ([Docker Hub](https://hub.docker.com/r/bkimminich/juice-shop)) |
| Execução            | Container Docker local, exposto apenas em `localhost:3000`              |
| Rede                | Rede Docker isolada (`es-seguro`), sem exposição para a internet        |
| Base de autorização | Aplicação criada e mantida pela OWASP justamente para treino em segurança |

**Nenhum sistema de terceiros foi testado.** O alvo roda na própria máquina de quem
executou a verificação, é acessível somente localmente e existe para esse fim.

O Juice Shop é uma loja online: tem catálogo, carrinho, contas de usuário, cesta e área
administrativa. Essa semelhança com o Comer-Tchê! é o que permite trazer os achados de
volta para o nosso modelo de ameaças.

### 18.2 Ferramenta e configuração do teste

| Item        | Valor                                                              |
| ----------- | ------------------------------------------------------------------ |
| Ferramenta  | **OWASP ZAP 2.17.0** (imagem `zaproxy/zap-stable`)                 |
| Modo        | `zap-baseline.py` — varredura **passiva**                          |
| Data/hora   | 11/08/2026, 20:47 UTC                                              |
| Escopo      | `http://juiceshop:3000` (a partir da rede interna do Docker)        |
| Saídas      | `relatorio-zap.html` e `relatorio-zap.json`                         |

Comando executado:

```bash
docker network create es-seguro
docker run -d --name juiceshop --network es-seguro -p 3000:3000 bkimminich/juice-shop

docker run --rm --network es-seguro -v "$PWD/zap-out:/zap/wrk:rw" \
  zaproxy/zap-stable zap-baseline.py \
  -t http://juiceshop:3000 -r relatorio-zap.html -J relatorio-zap.json -I
```

Escolhemos o **modo baseline** de propósito. Ele navega pela aplicação e analisa as
respostas, mas **não dispara ataques**: não injeta payloads nem tenta explorar falhas.
Isso atende ao enunciado, que diz que não é necessário explorar as vulnerabilidades nem
obter acesso indevido — o objetivo é interpretar os resultados.

### 18.4 Análise dos achados

Analisamos os três alertas de maior severidade e maior relação com o nosso sistema.

| ID  | Alerta ou achado | Evidência | Possível impacto | Relação com OWASP ou CWE | Correção proposta |
| --- | ---------------- | --------- | ---------------- | ------------------------ | ----------------- |
| A01 | Content Security Policy (CSP) Header Not Set — risco **Médio**, confiança alta | Resposta de `http://juiceshop:3000` sem o cabeçalho `Content-Security-Policy` (confirmado com `curl -I`) | Se existir uma falha de XSS, o navegador executa qualquer script injetado sem restrição: roubo de sessão, leitura de dados da tela e ações em nome da vítima | **A05:2021** Security Misconfiguration · **CWE-693** Protection Mechanism Failure | Enviar `Content-Security-Policy` restritiva, começando por `default-src 'self'`, sem `unsafe-inline`; publicar primeiro em modo `Report-Only` para medir quebras |
| A02 | Cross-Domain Misconfiguration — risco **Médio** | Cabeçalho `Access-Control-Allow-Origin: *` em `/`, `/robots.txt`, `/sitemap.xml` e `/styles.css` | Qualquer site consegue ler as respostas dessa origem a partir do navegador da vítima. Em uma API de pedidos, isso amplia qualquer falha de autorização, porque o dado vazado passa a ser legível por um site do atacante | **A05:2021** Security Misconfiguration · **CWE-264** Permissions, Privileges and Access Controls | Substituir o `*` por uma lista fixa de origens confiáveis (aplicativo e painel administrativo) e nunca combinar origem liberada com `Allow-Credentials: true` |
| A03 | Dangerous JS Functions — risco **Baixo** | Chamada a `bypassSecurityTrustHtml(` em `http://juiceshop:3000/main.js` | Essa função desliga explicitamente a sanitização automática do Angular. HTML vindo do usuário passa a ser renderizado como marcação, o que abre XSS mesmo com o framework oferecendo proteção por padrão | **A03:2021** Injection (XSS) · **CWE-749** Exposed Dangerous Method or Function | Remover o `bypassSecurityTrust*` e renderizar o conteúdo por interpolação normal; se a marcação for mesmo necessária, sanitizar no servidor com lista de permissão antes de gravar |

Observações sobre a interpretação, para não repetir o que a ferramenta diz:

- **O A02 é menos grave do que o rótulo sugere, neste caso.** Com `Access-Control-Allow-Origin: *`,
  o navegador **não** envia cookies nem cabeçalhos de autenticação na requisição
  cruzada — o próprio padrão CORS proíbe combinar `*` com credenciais. Ou seja, hoje o
  alerta atinge só conteúdo público. Ele continua valendo como correção porque o dia em
  que um endpoint autenticado herdar essa configuração, a falha vira séria e silenciosa.
- **O A01 não é uma vulnerabilidade por si só**, é a ausência de uma camada de defesa. Ele
  só causa dano combinado com outra falha — exatamente o argumento de defesa em
  profundidade: uma barreira que falha não deve derrubar o sistema inteiro.
- **O A03 é o único dos três que aponta código**, e não configuração. É também o mais
  próximo do que escrevemos na Etapa 4: a Prática 2 (validação de entrada) existe
  justamente para impedir que dado de usuário chegue cru a um ponto sensível.

### 18.5 Alertas descartados

Dos onze tipos de alerta, oito não entraram na análise principal. Os motivos:

| Alerta | Classificação | Por que foi descartado |
| ------ | ------------- | ---------------------- |
| Timestamp Disclosure - Unix | **Falso positivo** | O ZAP marcou o número `1528301887` dentro de `styles.css` como um timestamp Unix exposto. É apenas uma sequência de dígitos em uma folha de estilo; a regra sinaliza qualquer número de 10 dígitos. Não revela informação do sistema |
| Modern Web Application | Informativo | Apenas registra que a aplicação usa JavaScript pesado e que links podem não ser rastreáveis pelo spider. Não é falha |
| Storable and Cacheable Content · Storable but Non-Cacheable Content · Non-Storable Content | Informativos e sobrepostos | As três descrevem a mesma política de cache sob ângulos diferentes. Relevantes só se houvesse dado sensível em resposta cacheável, o que não é o caso nas URLs apontadas (`/robots.txt`, `/styles.css`, favicon) |
| Cross-Origin-Opener-Policy · Cross-Origin-Embedder-Policy Header Missing | Duplicados do A01 | São cabeçalhos da mesma família de isolamento de origem. A correção é a mesma frente de trabalho do A01, e tratá-los como achados separados inflaria a contagem sem acrescentar análise |
| Deprecated Feature Policy Header Set | Baixo, sem impacto de segurança | A aplicação envia `Feature-Policy: payment 'self'`, cabeçalho substituído por `Permissions-Policy`. É dívida técnica de padronização, não exposição |

### 18.6 Limitações desta verificação

O resultado mais importante desta etapa é **o que a ferramenta não encontrou**.

Nenhum dos seis riscos críticos do nosso registro (seção 8.4) apareceu no relatório. Não
por estarem resolvidos, mas porque uma varredura passiva não consegue vê-los:

- **R07 (IDOR) e R10 (elevação de privilégio)** exigem duas contas autenticadas e o
  conhecimento de qual recurso pertence a quem. O ZAP não sabe que o pedido `1002` deveria
  ser invisível para o cliente do pedido `1001` — isso é regra de negócio, não padrão de
  resposta HTTP.
- **R01 (uso indevido de conta)** depende de testar credenciais, o que a ferramenta não faz
  em modo baseline.
- **R09 (indisponibilidade no pico)** só apareceria em um teste de carga, que é outro tipo
  de ensaio.

Outras limitações da sessão:

1. **Sem autenticação.** O ZAP navegou como visitante anônimo, então toda a área logada
   ficou fora do alcance.
2. **Sem varredura ativa.** Não houve injeção de payloads, então SQL Injection e XSS
   refletido não seriam detectados mesmo se existissem — e o Juice Shop tem os dois.
3. **O alvo não é o nosso sistema.** Os achados valem como aprendizado sobre classes de
   problema e sobre como interpretar a ferramenta, não como um retrato do Comer-Tchê!.

A conclusão prática é que **ferramenta automatizada e modelagem de ameaças são
complementares, não substitutas**. O ZAP encontrou em minutos três problemas de
configuração que o nosso STRIDE não tinha listado — nenhuma das onze ameaças da Etapa 1
falava de cabeçalhos HTTP. Em compensação, ele foi cego justamente para os riscos que
classificamos como críticos, porque eles dependem de entender o negócio. Confiar só na
ferramenta daria um sistema com cabeçalhos exemplares e um IDOR expondo a base inteira de
clientes.
